## 已经在线运行的改动

| 改动 | 上游 v0.3.27/v0.3.30 的相关行为 | 我们的行为 | 代码落点 |
| --- | --- | --- | --- |
| Planner 职责收紧 | 装配默认文件/命令工具，允许 WebFetch，搜索按配置启用 | 原生白名单和 PreToolUse 检查；执行由 Worker 完成 | `agent/planner.go`、`agent/planner_policy.go` |
| Planner 空转控制 | 无本分支的六次宽泛读取规则和 planner_decision | 空队列最多六次不同宽泛检索；可定点读证据，也可明确缺前提后结束 | 同上 |
| Planner 预算 | 无独立默认墙钟限制；轮数按原配置 | 主阶段默认16轮、240秒，另有有限收尾；不是绝对总时限 | `agent/planner.go`、线上 Agent 配置 |
| 历史读取成本 | 无本分支单轮读取缓存与概览裁剪 | 单轮缓存、版本失效、最多64项；旧 digest 概览最多400字，可展开 | `agent/planner_policy.go`、`db/planner_read_revision.go` |

| 跨任务经验库 | 无本分支经验扩展 | 报告/任务提炼候选方法；来源版本、脱敏、作用域、撤回、审核、反馈 | `extensions/experience/` |

目标拆解、探索图、Worker池、工具审查、报告、复测、资产/流量记录、任务继承等基础能力来自上游。尤其 `finding_workflow`、报告证据交接和独立审查模型不是本分支原创；不能因为本分支文档介绍了它们，就算作新增优化。相对 v0.3.27，线上分支的 Worker 主执行和 fact 写入代码没有核心改造。

## 核对时尚未上线的 v5 工作

以下在工作区实现并做隔离验证，核对时尚无线上 `curation_runs` / `intent_experiences` 表，也没有新二进制：

- 宿主准备来源，数据库记录 saved/partial/skipped/failed/no_source；只说“完成”不能记为入库。
- 经验角色硬工具白名单，发布批次由宿主绑定。
- `add_intent.experience_refs`，创建意图与采用记录同事务提交；冻结有限方法摘要。
- Worker完成后关联真实结果，先进入待评价；不自动登记 helpful。
- 稳定意图级否定/部分结果来源，中文别名映射，以及30条合成检索样本。

这些验证证明特定软件行为，不证明真实解题成功率提高。对照样本的同义词召回结果也不能直接推广到真实经验库或所有CTF题。

## 上游最新版已有、我们尚未合入的内容

上游 v0.3.28：英文界面、完整流量ID显示/搜索、过滤统计一致性、Basic Auth恢复等。

上游 v0.3.29：可选无成果止损、任务文件只读浏览/下载、旁路问答摘要重试。

上游 v0.3.30：可选外部 MCP 服务端（区别于原本的 MCP 客户端工具接入）、访问令牌及来源白名单、统一 HTTP User-Agent、解码后工具字符串的拦截匹配、代理 SOCKS5失败修复（go-mitmproxy v1.9.5）。

因此我们是基于旧基础的专用分支，不能称为 v0.3.30 的完整增强版。合并上游需要保留 Planner/复盘边界并逐项回归，不适合直接覆盖生产。

## 线上收益证据与缺口

截至核对时：

- 有效候选152条，其中 success149、inconclusive3；有效 negative 为0；另有 deprecated75条。这里的 success 是经验卡片结果标签，不是独立验真。
- 方法审核记录0条，verified0条。
- 最近24小时 retrieved45条、adopted0条、helpful0条、not_applicable2条。retrieved按卡片记，不是45次独立查询；adopted依赖旧模型手工反馈，0条只能证明没有登记，不能证明从未借鉴。
- 累计 adopted5条，集中在1个任务；累计 helpful4条，其中较新的2条绑定了结果节点，另2条是旧格式。均无独立方法审核，不能作为受控成功率。
- 整理器确实每小时执行，并有保存2条 candidate 的真实记录。最近两轮分别出现快照读取错误和发布超时；通用工具/会话仍可能显示 `is_error=false`，所以运行结束不能当作整理成功。
- 随后核对最近24小时的957条执行结果，67条包含上游503和“没有可用账号”错误；这是模型服务可用性问题。未更换用户模型、凭据或账号池，不能用经验架构改动替代上游恢复。

结论：这些改动已提供规划控制、复盘和可检索存储，但“越用越会解题”尚无证据。当前薄弱环节是整理可靠交付、从检索到采用/结果的关联、有效失败卡覆盖和独立效果评估。Planner的限制减少无界读取，也可能压缩复杂推理时间；不能只看耗时下降就判定解题能力提高。
